# Trudvang project instructions

- Do not control the user's interface or access the Foundry installation (even read-only) without the user's explicit prior permission for that action. Work and test inside this repository using isolated previews; touching the installed application is a last resort for a stubborn bug, never a routine verification step.
- Before implementing or reviewing any game-rule behavior, search `game doc/markdown/` (English books) and `game doc/markdown-fr/` (official French edition; the « Livre des règles » combines the Player's Handbook and Game Masters Guide) for the relevant rule and page references. The French edition is the terminology authority.
- When text extraction is ambiguous, a diagram or table controls the interpretation, or an exact visual structure matters, inspect the corresponding source PDF with the PDF skill.
- Treat `game doc/markdown/` and `game doc/markdown-fr/` as generated reference material. Regenerate them with `tools/extract_pdf_rules.py` after any source PDF changes.
- Keep all user-facing strings in `lang/en.json` and `lang/fr.json`, including starter content and the tablet catalogue (`TRUDVANG.Content.*`: names, themes, power summaries). `modules/tablet-catalog.mjs` holds only structural data (ids, levels, costs, religions, pages) — never display text.
- Before adding or changing language entries, consult `lang/GLOSSARY.md` and preserve its established terminology. Update the glossary whenever translated terminology changes; regenerate it with `node tools/generate-glossary.mjs --write`. Power summaries (`TRUDVANG.Content.Power.*.Summary`) are rule quotations and are excluded from the glossary.
- Foundry API compatibility: never use an API marked as deprecated (check console `logCompatibilityWarning` and the V13→V16 migration guides on foundryvtt.wiki). When adding code that hooks construction-time events (directory context menus via `getDocumentContextOptions`, etc.), register the `Hooks.on` at `init` or module top level — never in `ready` — because those menus are built once at first render, before `ready` fires, and a late registration silently never runs. Target is the current stable (V14) but every implementation must be future-proof for the next major (V16): use the namespaced ApplicationV2 stack (`HandlebarsApplicationMixin(ActorSheetV2/ItemSheetV2/ApplicationV2)`, `foundry.applications.api.DialogV2`, `foundry.applications.handlebars.renderTemplate`, `foundry.applications.ux.TextEditor.implementation`, `DocumentSheetConfig` + `renderChatMessageHTML`, etc.). Keep V14 fallbacks (`foundry.appv1`/`globalThis.Dialog`/`global renderTemplate`) only in dead `else` branches that never execute when the new API exists — never as active code.
- Git layout: `origin` is the public repository, `backup` (Trudvang-Chronicles-Dev) mirrors the same commits — always push both. `game doc/` is a separate nested private repository; never commit its contents to the outer repository.
- Windows toolchain: the embedded MinGit is configured with `GIT_EXEC_PATH` pointing to its own `mingw64/bin` and an OpenSSL HTTPS backend using its shipped CA bundle; this fixes missing `remote-https`, the credential manager's child-Git launch, and sandbox Schannel failures while retaining certificate verification. Windows Credential Manager (`wincredman`) still refuses access inside the sandbox: for authenticated GitHub fetch/push and releases, use `exec_command` with `sandbox_permissions: "require_escalated"`. To test/use embedded Git there, invoke its executable explicitly and keep its matching `GIT_EXEC_PATH`; when using the installed Windows Git, remove `Env:GIT_EXEC_PATH` in that shell so its helpers come from the same installation. Never disable certificate verification or copy credentials into the sandbox. If sandboxed npm fails because of inherited `OPENSSL_CONF` / `OPENSSL_MODULES` or an inaccessible roaming npm installation, remove those two variables from that shell's environment and set `npm_config_prefix` to the selected Node installation directory (derive it from `Get-Command node`); these adjustments apply only to the tool environment. Runtime updates may replace the embedded Git config: recheck its helper path and HTTPS backend before assuming that it is corrupt. Run `npm run check` and the usual release script with the working Windows toolchain.
- Versioning: small fixes and tweaks bump only the patch number (`0.1.x`); reserve the minor number (`0.x.0`) for substantially larger feature implementations. For a major overhaul, ask the user before changing the leading number. Every version bump is released: after pushing `main`, always push the matching `v<version>` tag on `origin` (the GitHub Actions workflow then validates, packages, and publishes automatically). Releases are automated — run `npm run release <x.y.z|patch|minor> ["sujet"]`: it bumps `system.json`, validates, commits all pending changes, tags, pushes both remotes plus the tag, and verifies the remote state; never hand-roll this sequence.
- After any non-trivial task, increase the minor version number. After large changes, prompt the user if you should increase the major version.
- Keep [`docs/development-world-migrations.md`](docs/development-world-migrations.md) complete whenever adding, changing, or removing code that exists only to migrate a previously created development world. Such code must also carry a nearby `TEMPORARY WORLD MIGRATION` comment.
